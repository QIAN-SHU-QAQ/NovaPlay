## 1. 建议的定位

把项目做成 **Windows 上可靠、易用的个人追番播放器**：找到作品，确认作品和剧集，顺利播放，关掉后能接着看，需要时能离线保存。

目前的优势是已打通浏览、播放、历史、收藏、下载和独立播放窗口，且有离线测试及实际 Windows 回归记录。下一阶段的主要价值在于让这些功能在地址失效、网络恢复、进程重启和升级后仍然可靠，并让普通用户拿到可运行的软件。

可以选择的三条路线：

| 路线 | 用户获得的价值 | 代价与取舍 | 建议 |
| --- | --- | --- | --- |
| 先提高可靠性并发布 Windows 预览版 | 少丢进度、少错集，下载后即可使用 | 新功能数量增长较慢 | **当前优先** |
| 先做追番管理与新番发现 | 想看/在看/看完、更新提醒、季度浏览 | 要先解决作品身份和资料匹配，否则列表会重复、错季 | 发布预览版后推进 |
| 先扩展跨平台、账号和同步 | 多设备使用与数据漫游 | 新增平台交互、发布、认证、服务运维和冲突处理成本 | 暂缓 |

第一阶段维持现有 Flutter、Riverpod、media_kit 和独立播放器方案，针对已经找到的问题改进；存储层逐步建立可替换边界。

## 4. 优先解决的具体问题

这里的 P1 表示应在下一轮优先处理的用户数据或文件正确性问题；P2 表示后续功能完善或公开预览版前需要处理的问题。

### P1：离线旧历史可能覆盖已经提交的新历史

依据：[database_service.dart](../../lib/services/database_service.dart) 的 `_dispatchOp()`、`_flushPendingOps()` 和 `_saveHistoryLocal()`。

诊断过程使用可切换在线状态的客户端替身：先离线保存 10 秒进度，操作进入积压队列；恢复在线后保存 20 秒进度，新操作直接发送成功；3 秒定时重试随后发送积压的 10 秒记录。按接受顺序调用真实的主进程合并方法后，最终保存成 10 秒。这是客户端队列与服务端合并边界的受控复现，本轮未重新操作真实窗口重启。

根因是有积压时新操作仍可直接发送，历史合并又按到达顺序覆盖，同一作品没有新旧操作判断。PR #6 的端点重连已起作用，但“能重连”和“重连后操作顺序正确”是不同验收项。

建议：同一客户端的写入和补交共用有序队列；每条操作有稳定 ID、客户端序号和可重试确认机制。历史合并增加明确的版本规则。并发补交只删除已经确认的批次，审查目前 `_pendingOps.clear()` 是否可能清掉请求期间新加入的操作。

验收必须覆盖：10 秒离线、20 秒在线、旧操作晚到后仍保留新记录；用户后来主动回退至 5 秒时，又必须允许保存 5 秒。不能简单取最大播放位置。同时测试请求应用成功但响应丢失、离线跨集、删除后旧日志重放。

### P1：断点下载可能把旧清单分片与新清单分片混拼

依据：[m3u8_downloader.dart](../../lib/services/m3u8/m3u8_downloader.dart) 第 119 行附近。复用条件只有“按序号命名的文件存在且非空”。

诊断预置第 0 片旧内容 `[9]`，重新获取的清单内容应是 `[1,2]`。下载器跳过新的第 0 片，最终报告完成，产物却是 `[9,2]`。恢复时 CDN 清单变更、版本切换，或分片文件在上次中断时未完整写入，都需要校验。

建议：保存任务清单指纹、媒体序号、分片 URI、长度及校验信息；分片先写临时文件，成功后再提交为可复用文件。清单变更时确认同一作品、同一集及分片身份，无法确认时提示重新开始。不要只凭数组位置复用。

验收：清单重排、URI 变化、同 URI 内容变化、截断文件和进程中断后均不静默产生混合文件；不一致的分片必须重新下载或明确停止任务。

### P2：下载器会把部分不支持的 HLS 格式当成成功

依据：[m3u8_parser.dart](../../lib/services/m3u8/m3u8_parser.dart) 第 119 行附近忽略未识别的标签，下载器把取得的内容顺序拼成 `.ts`。

诊断输入带 `EXT-X-MAP` 的 fMP4 清单，初始化段为 `[1,2]`、媒体片段为 `[3,4]`。下载报告成功，却完全没有请求初始化段，输出仅 `[3,4]`。

建议：先把支持范围限定为经过验证的未加密、完整 TS VOD；对 fMP4/MAP、BYTERANGE、独立音轨及直播等逐一明确处理或拒绝。discontinuity 的兼容性另用真实样本验证，不因一次拼接能播放就泛化支持。

验收：不支持的输入在下载主体前得到明确错误，任务不能显示“已完成”；支持格式应验证可播放、可拖动并能播到结尾。

### P2：弹幕匹配会混淆季度，也没有拒绝无关候选的下限

依据：[dandanplay_client.dart](../../lib/services/danmaku/dandanplay_client.dart) 第 247 行附近删除季号，`pickBestMatch()` 总会在非空候选中选一个。

诊断请求“测试动画 第二季 / 第 1 集”，候选顺序为第一季、第二季，实际选到第一季；候选只有完全无关作品时也会接受。这里确认的是匹配逻辑，不依赖真实服务是否恰好返回这些候选。

建议：保留季度、年份、TV/剧场版/SP 等身份信息；冲突候选排除，不确定就允许无匹配；增加手动选择作品和剧集、保存关联及解除关联。之后再补偏移、屏蔽词、密度和有界缓存。

验收：相同第 1 集不会跨季；无关结果不能自动套用；手动纠正重启后保留；暂停、seek、倍速及切集都以视频时间为准。现有渲染测试主要检查不抛异常，应增加可观察的投递与同步断言。

### P2：配置桥的会话字段仍可省略

依据：[prefs_bridge.dart](../../lib/services/prefs_bridge.dart) 第 161 行附近，仅在传入值是字符串且不相等时拒绝。

诊断使用项目已有客户端、不提供端点文件，发送无 session 的 `set` 请求，服务端接受并执行写入回调。之前“旧 token 被拒绝”的验收结论成立，但不能推导为所有请求都经过强制会话校验。

建议：正式协议要求有效会话，缺失、空值、错误类型均拒绝；旧协议兼容必须明确限制。增加允许写入的键和操作、输入结构与大小限制、连接超时。端点缺失时优先进入离线队列，避免固定端口兜底绕过会话。

验收：缺失、非字符串、空 token、旧 token 均失败；当前 token 与允许的操作成功。服务只监听 loopback，这不是已证实的远程攻击入口，也不是完整安全审计结论。

### P2：失效地址续播与资料匹配仍没有完成

依据：[play_launcher.dart](../../lib/core/utils/play_launcher.dart) 的 `launchHistoryResume()` 直接采用历史快照地址；[bangumi_api.dart](../../lib/services/bangumi_api.dart) 的搜索直接取首项。后者用 `Future.wait` 同取详情和角色，一个失败会使整份资料返回空。

建议：增加统一的续播解析服务，按完整来源 ID 重新获取详情，确认原集后使用新 URL 并恢复位置。Bangumi 返回候选并允许纠正；角色请求失败时保留已取得的标题、评分等内容。

验收：首页、历史、收藏三个入口行为一致；地址过期、剧集重排、缺集、重复集名均不会误播其他集；请求中离开页面不再自动开窗；资料错季可纠正且不会改变视频源身份。

### 第二轮：交付首个 Windows 预览版

当前 CI 只运行格式、分析和测试，没有 `flutter build windows --release`；工作流依赖获取也没有强制 lockfile。查询时 GitHub 没有 Release。

建议增加受支持的明确 runner/Flutter 工具链组合、锁定依赖构建、便携 ZIP、SHA-256、变更记录和手动触发的 draft Release。先在干净 runner 上验证，不能依赖本机 Flutter 的 VS 2026 补丁。

分发包要包含完整 exe、DLL、data 和许可说明；解压到包含中文与空格的运行目录，在没有 Flutter/VS 的 Windows 环境验证启动、搜索、在线播放、下载后断网播放、历史/设置保存和二次启动。构建时的 ASCII 路径要求与用户运行路径分别验证。

现有 [deploy-release.ps1](../../scripts/deploy-release.ps1) 是本机部署脚本：硬编码 E 盘默认路径、按进程名关闭程序、清空目标目录。应改成显式路径校验和仅操作目标程序目录，或由新打包脚本独立承担分发；本轮没有执行该脚本。

首个预览版附已知限制和反馈模板。先获得真实使用反馈，再安排安装器与自动更新；自动更新需要版本校验、失败恢复和旧版保留，不能只增加“下载新 exe”按钮。

### 第三轮：形成追番工具的特色

按用户收益优先增加：

| 项目 | 第一版范围 | 验收条件 |
| --- | --- | --- |
| 追番清单 | 想看、在看、看完、搁置；手动状态与已看集数 | 多季度分别管理；换源不产生另一份同作品记录 |
| 更新发现 | 对已关注作品比较可用集数，显示新增集数 | 上次检查时间与源失败可见；列表重排不误报更新 |
| 作品资料关联 | 手选 Bangumi 与弹幕对应作品/剧集 | 能保存、纠正、清除关联；季度冲突不会自动套用 |
| 下载体验 | 自选路径、容量提示、去重、缺失文件识别 | 已有任务不重复加；文件被外部删除时显示实际状态 |
| 数据保护 | 收藏/历史/追番列表导出和导入 | 预览合并结果、格式版本校验、导入失败不破坏原数据 |
| 故障诊断 | 可复制的版本、错误类别、源状态和脱敏日志 | 排除 AppSecret、带签名 URL 及个人历史，导出前可查看 |

“清除已完成”目前会删除任务对应的本地文件，而不只是清理列表，见 `DownloadService.clearCompleted()`。应区分“移除记录”和“删除本地文件”，明确文案与用户选择，避免下载体验造成误删。

暂不优先：账号云同步、社交社区、插件市场、全平台适配、AI 推荐和大范围 UI 重写。后续有明确使用需求时再评估。

## 6. 技术改进应服务于上述交付

### 存储与进程边界

保留“主进程合并语义操作”的原则，补齐有序交付、幂等确认和恢复。增加两个主窗口同时启动、主进程强杀、子进程写日志期间主进程回放等专项测试；目前没有把这些情形视为已验证通过。

建议抽出 `HistoryRepository`、操作队列和 journal 存储接口，主题等简单偏好继续使用偏好存储。收藏、历史、下载任务逐步评估迁移到支持事务和版本迁移的结构化存储。先做旧数据迁移测试、备份与回滚路径，避免一次迁移造成数据丢失。

依据是项目已经在偏好存储外增加多进程协调、离线回放和手工列表合并。插件官方文档也明确提示异步落盘的保证有限，并说明缓存会引入多个执行环境之间的一致性问题：[shared_preferences 文档](https://pub.dev/packages/shared_preferences)。仅升级 API 不能替代本项目需要的事务、操作顺序和业务冲突规则。

### 播放器职责与测试能力

`player_screen.dart` 当前约 1,039 行，`database_service.dart` 约 615 行。已有 `PlaybackSession` 和 `FullscreenSession` 是良好拆分基础；下一步将弹幕请求/匹配、历史保存调度、设置应用继续移出页面，让页面主要负责交互和展示。

注入弹幕客户端、时钟和进程启动器，便于验证超时、旧响应、重复点击与退出。优先覆盖本次出现的真实边界，不以文件行数或测试数量作为重构目标。

### 文档和协作

更新开发报告，把旧计划中已经交付的分页、播放设置、下载和弹幕标为已有基础实现，再保留真正未完成的验收条件。旧计划中的方案与当前实现也有差异，例如旧方案设计本地 HLS 清单，当前实现采用 TS 拼接，应保留决策与支持范围。

为外部贡献者补充 `CONTRIBUTING.md` 和 PR 模板：说明环境、锁定依赖、离线测试、真实服务验证如何分开，以及跨进程、下载和用户数据变更的回归要求。优先采用小范围 PR，合并后验收与合并前自动检查都保留。

依赖升级另开 PR，先核对 Flutter、Dart 与 Windows 插件兼容性，再做完整回归。不能因为依赖解析提示多个新版本，就混入业务修复批量升级。

## 7. 验收用例与完成标准

所有样例使用项目自制或允许使用的媒体、临时目录和测试配置，不把个人历史、凭据或真实带签名地址放进仓库。自动化通过依赖断言最终数据、文件内容与请求顺序，不能只判断“不抛异常”。下列 A1–A8 都是待执行要求。

### A1：历史有序补交与恢复（R1）

- [ ] 自动化：客户端离线保存 10 秒，恢复后提交 20 秒，再触发旧操作重试；最终为 20 秒。随后主动回退并保存 5 秒，最终应为 5 秒。
- [ ] 自动化：服务端已经应用操作但响应丢失，重试不能重复插入或覆盖更新记录；补交进行中新增的操作不能被清空。
- [ ] 自动化：删除前的旧日志不复活已删除记录；覆盖离线切集、两个客户端更新同一作品，并在 PR 写清冲突规则。删除之后的新观看按公开约定处理。
- [ ] 实机：保留两个播放器，关闭主窗口至少 15 秒后重开，连续两轮；两条历史、主窗口新增收藏保留，连接恢复后 15 秒内积压日志清空，随后至少观察 15 秒无旧记录回退。
- [ ] 实机：主窗口退出期间产生进度，再结束播放器并重开主窗口，最后一次已确认落盘的进度可恢复；强制结束另测并记录可能损失的未落盘时间范围。
- [ ] 进程边界：同时启动两个主窗口，应明确只保留一个持久化写入方，或提供已验证的多主窗口一致性方案。

### A2：下载分片身份与完整性（R2）

- [ ] 自动化：缓存旧分片 `[9]`，新清单两片内容为 `[1]`、`[2]`；完成产物只能是 `[1,2]`，或明确要求重新开始，不能以 `[9,2]` 报告完成。
- [ ] 自动化：覆盖清单重排、分片地址变化、截断缓存和清单损坏。仅文件非空不能作为复用依据。
- [ ] 自动化：同 URI 内容变化且无可靠验证信息时，重新下载或停止并提示，不能声称已经验证旧分片可复用。
- [ ] 自动化：模拟写盘中断、目录不可写和空间不足；任务显示可理解的失败状态，临时文件不得被当作完成分片。
- [ ] 实机：下载途中暂停、退出、重开并继续；进度与实际分片一致。至少包含一次非正常中断恢复；完成文件与同一固定样本全量下载的哈希一致。

### A3：HLS 格式边界（R3）

- [ ] 自动化：TS VOD 的相对地址、主列表选择及分片顺序正确；空清单、格式错误、加密清单有明确失败。
- [ ] 自动化：为 `EXT-X-MAP`/fMP4、`BYTERANGE`、独立音轨、直播和 discontinuity 分别建立样本；逐项声明支持或拒绝。不支持的输入不得生成“完成”任务。
- [ ] 自动化：声明支持 MAP 时必须请求并按格式处理初始化段；否则在主体下载前拒绝。不能漏掉初始化段后报告成功。
- [ ] 实机：对声明支持的每类样本，下载后断网播放、seek 至中间及接近结尾，并播放到结束。保存清单、文件哈希和操作结果。

### A4：刷新地址后恢复原集（R4）

- [ ] 自动化：历史第 2 集旧 URL 失效，最新详情第 2 集换为新 URL；只打开新地址，原进度保留。
- [ ] 自动化：最新剧集列表重排仍定位原集；缺集、重复标题、空快照、来源不符时引导重新选集，不默认播放第一集，不破坏旧进度。
- [ ] 自动化：双击只创建一次播放请求；准备中离开页面不再开窗；刷新失败可重试，重试重新获取详情。
- [ ] 实机：首页、历史页、收藏页逐一续播；固定源模拟地址轮换和列表重排，核对作品名、集名、URL 与恢复位置。

### A5：弹幕匹配、纠正和同步（R5）

- [ ] 自动化：候选第一季排在第二季前，请求第二季第 1 集不能选到第一季；只有无关作品时返回无匹配或要求手选。
- [ ] 自动化：覆盖别名、年份冲突、TV/剧场版/SP、缺字段及多个相近候选；手动关联、解除和重启恢复均有断言。
- [ ] 自动化：用受控视频时间验证暂停、继续、前后 seek、倍速和切集；旧集晚到响应不能覆盖当前集，重复弹幕不重复投递。
- [ ] 实机：用有效测试凭据验证真实服务鉴权、正确季度与集数、滚动显示和密集场景；服务失败可见且不影响视频播放。未配置凭据不能发起无效请求，关闭弹幕后不继续不必要的数据请求。
- [ ] 证据：记录样本集、弹幕数量、机器与帧时间；凭据和签名参数脱敏。缺少凭据时把真实服务项标为“未验收”，不以 mock 结果替代。

### A6：配置桥协议与重连（R6）

- [ ] 自动化：session 缺失、空值、错误类型、旧 token 均拒绝，且不触发写入；正确 token 与允许操作成功。
- [ ] 自动化：不允许的键或操作、畸形输入、超出声明大小的输入均拒绝且不修改数据；没有完整请求的连接会在声明超时内关闭。
- [ ] 自动化：端点文件缺失、损坏或会话过期时，操作留在离线队列；恢复有效端点后补交，顺序满足 A1。
- [ ] 实机：保留同一批两个播放器，连续两次重启主窗口；旧播放器发现新端点，恢复实时进度，历史和收藏不丢失。

### A7：Bangumi 资料关联与降级（R7）

- [ ] 自动化：同名不同年、不同季、TV/剧场版、零候选和多候选不会直接套用搜索首项；不确定时可不显示资料。
- [ ] 自动化：手选 subject ID 按完整视频 ID 保存，重启可恢复，清除关联后可重选；不修改视频源作品身份。
- [ ] 自动化：分别模拟搜索、详情、角色请求失败；角色失败时仍能显示已经取得的标题和评分，网络失败不清除用户确认的关联。
- [ ] 实机：两季作品分别纠正资料并重启核对；断网或接口失败时视频选集与播放仍可用。

### A8：Windows 便携版交付（R8）

- [ ] CI：干净 Windows runner 从精确提交执行锁定依赖解析、格式、分析、测试和 Release 构建，保存运行链接及工具链版本；不依赖开发者本机 SDK 补丁。
- [ ] 打包：完整运行目录、许可、使用说明、版本化 ZIP 和 SHA-256 齐全；没有历史、缓存、日志或凭据。缺失 exe/DLL/data 时打包失败。
- [ ] 干净机器：没有 Flutter/VS，在含中文及空格的路径解压，验证启动、搜索、在线播放、切集、全屏、离线播放、收藏/历史/设置保存及二次启动。
- [ ] 升级：使用测试旧数据升级到新包，收藏、历史、设置和下载任务可读，旧下载路径有效；迁移失败时保留原数据。
- [ ] 发布：先创建 draft 并核对资产；验收记录注明 Windows 版本、包哈希、测试提交、运行库需求和已知限制，再由维护者决定公开。仅 CI 构建通过不能勾选干净机器验收。

### 每个 PR 的统一交付要求

在仓库根目录执行，并在 PR 附实际结果：

```powershell
flutter pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
flutter build windows --release --target lib/main.dart
git diff --check
```

修复代码必须附目标回归测试的修复前失败、修复后通过证据。纯文档 PR 检查差异、链接与文档一致性即可，不要求重跑应用测试和构建。依赖升级单独提交，不能混入无关 lockfile 更新。

PR 验收记录使用下面的格式，未执行项明确保留：

```text

测试提交 SHA：
```

贡献者提交证据，维护者复核，并在合并后的主分支重跑受影响实机场景后更新状态。不要只以“CI 绿了”或“测试数增加”作为完成标准。
